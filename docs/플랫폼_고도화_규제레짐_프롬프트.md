# 플랫폼 고도화 — 규제 레짐 확장과 추가 프롬프트

**목표**: 화장품 전용 도구를 여러 화학제품 카테고리로 확장하되, **1인 · 홈 개발 · OEM 양산** 방향성에 맞는 것만 넣는다.

---

## 1. 먼저 — 어떤 제품까지 넣을 것인가

확장하기 전에 이걸 정해야 합니다. 조사해보니 **카테고리마다 적용되는 법이 다르고, 비용 차이가 수십 배**입니다.

|---|---|---|---|---|---|

### 그래서 답

**샴푸는 넣으세요.** 화장품이라 **추가 등록 비용이 0원**입니다. 이미 만든 화장품 레짐이 그대로 적용되고, 계면활성제와 컨디셔닝 폴리머라는 새 원료군만 추가하면 됩니다. 방향성에 완벽히 맞습니다.

**탈취제는 넣으세요.** 다만 화장품과 **다른 법**입니다. 제품별·배합별 신고고 3년마다 갱신입니다. 21~48.5만원이면 감당 가능하지만, **SKU를 늘릴 때마다 돈이 나갑니다.** 플랫폼이 이 비용을 자동으로 계산해줘야 하는 이유가 여기 있습니다.

**섬유유연제는 빼세요.** 계면활성제 함유 기준 **197만원 + 40일**입니다. 예산 1천만원의 20%가 향 하나에 들어갑니다. 세탁세제도 105만원 + 40일이라 마찬가지입니다. 이 카테고리는 대량 물류와 가격 경쟁이 지배하는 시장이라, 1인 창업이 이길 구조가 아닙니다.

**살균·살충 계열은 절대 빼세요.** 이건 신고가 아니라 **승인**입니다. 독성·효능 자료를 갖춰야 하고 처리에만 약 12개월이 걸립니다. 미승인 제품은 제조·수입·판매가 전면 금지됩니다. "천연 방충 스프레이" 같은 아이디어가 여기 걸립니다.

**치약·손소독제도 빼세요.** 의약외품이라 약사법 영역이고 제조업 신고와 품목허가가 별도입니다.

## 2. 아키텍처 — 레짐을 플러그인으로 분리

지금 코드는 화장품 규정이 곳곳에 박혀 있을 겁니다. 이걸 **레짐 추상화**로 빼내는 게 고도화의 전제입니다. 이 리팩터링을 안 하고 탈취제를 추가하면 `if product_type == "cosmetic"` 분기가 코드 전체에 번집니다.

```
src/brandlab/
├── core/                     # 레짐 무관
│   ├── models.py             # Formula, Ingredient, Packaging
│   ├── scaling.py            # 배치 계산
│   └── costing.py            # 원가
├── regimes/
│   ├── base.py               # Regime 프로토콜
│   ├── cosmetics.py          # 화장품법
│   ├── chemical_safety.py    # 화학제품안전법 (안전확인대상)
│   ├── unsupported.py        # 살생물제·의약외품 → 명시적 거부
│   └── registry.py
├── advisor/
│   └── regime_advisor.py     # ★ 제품 아이디어 → 레짐 판정 + 비용 비교
└── pipeline/                 # 제품별 진행 상태
```

각 레짐이 구현할 인터페이스:

```python
class Regime(Protocol):
    code: str                  # "cosmetics" | "chemical_safety"
    law_name: str

    def validate(self, product) -> list[Finding]: ...
    def label_spec(self, product) -> LabelSpec: ...
    def entry_cost(self, product) -> CostBreakdown: ...
    def lead_time_days(self, product) -> int: ...
    def sku_expansion_cost(self, product) -> int: ...   # ← 핵심
    def renewal_period_years(self, product) -> int | None: ...
```

`sku_expansion_cost`가 핵심입니다. 화장품은 0원, 생활화학제품은 품목·배합마다 수십만원. **이 한 줄이 제품 전략을 결정합니다.**

### 프롬프트 9 — 규제 레짐 추상화 리팩터링 ★ 전제 조건

```
brand-lab을 여러 제품 카테고리로 확장하려고 한다. 지금은 화장품 규정이
코드 곳곳에 박혀 있는데, 이걸 레짐(regulatory regime) 플러그인 구조로
리팩터링해야 한다.

## 배경
내가 다룰 제품은 두 개의 서로 다른 법 아래 있다.
- 화장품법: 샴푸, 컨디셔너, 바디워시, 클렌징밤, 립밤, 오일, 화장비누, 향수
  → 영업자 등록제. 한 번 등록하면 SKU를 몇 개 내든 추가 비용 0원.
- 화학제품안전법(안전확인대상생활화학제품): 탈취제, 방향제, 초
  → 제품별·배합별 신고제. 품목마다 시험비가 들고 3년마다 갱신.

이 차이가 제품 전략을 결정하기 때문에 코드 구조에 반드시 반영돼야 한다.

## 요구사항

1. src/brandlab/core/ 로 레짐 무관 로직을 분리할 것
   (모델, 배치 스케일링, 원가 계산 — 이건 어떤 법이든 동일하다)

2. src/brandlab/regimes/base.py 에 Regime 프로토콜을 정의할 것:
   - code, law_name, display_name
   - validate(product) -> list[Finding]
       Finding은 level(error/warning/info), code, message, reference를 가진다
   - label_spec(product) -> LabelSpec   # 라벨 필수 기재 항목
   - entry_cost(product) -> CostBreakdown
   - lead_time_days(product) -> int
   - sku_expansion_cost(product) -> int   # 새 SKU 1개 추가 시 규제 비용
   - renewal_period_years(product) -> int | None

3. regimes/cosmetics.py — 기존 화장품 로직을 전부 이쪽으로 이동
   - sku_expansion_cost는 0을 반환
   - renewal_period_years는 None

4. regimes/unsupported.py — 명시적으로 지원하지 않는 레짐
   - 살생물제품(살균제·살충제·방충제·기피제): 승인제, 약 12개월, 고액
   - 의약외품(치약·손소독제 등): 약사법, 제조업 신고 + 품목허가 별도
   - 이 레짐으로 제품을 만들려 하면 validate가 error를 반환하고
     "이 카테고리는 1인 창업 규모에 맞지 않습니다. 이유: ..." 를 설명할 것
   - 조용히 통과시키지 말 것. 이게 이 모듈의 존재 이유다.

5. regimes/registry.py — 레짐 등록과 조회. 새 레짐 추가가 파일 하나 추가로
   끝나야 한다.

6. Formula 모델에 regime 필드를 추가하고, 기존 처방 YAML을 마이그레이션할 것
   - 마이그레이션 스크립트를 만들고, 원본을 .bak으로 백업할 것

7. 규제 수치는 여전히 data/regulatory/<regime_code>/ 아래 YAML에서 읽을 것.
   코드에 하드코딩 금지. 각 파일에 last_updated와 source_url을 필수로 둘 것.

## 검증
- 기존 화장품 기능(전성분, 알러젠, 원가)이 리팩터링 후에도 동일하게 동작하는지
  기존 테스트가 전부 통과할 것
- 지원하지 않는 레짐으로 제품을 만들면 error가 나오는지 테스트
- 새 레짐을 추가하는 것이 registry에 한 줄 추가로 되는지 확인하는 테스트

기능을 추가하지 말 것. 이번 단계는 순수 리팩터링이다.
```

### 프롬프트 11 — 규제 판정 엔진 (RegimeAdvisor) ★ 이 플랫폼의 심장

```
brand-lab에 제품 기획 단계에서 쓸 규제 판정 엔진을 추가한다.
이게 이 플랫폼에서 가장 가치 있는 기능이다.

## 문제
같은 향을 팔더라도 "향수(화장품)"로 내면 등록 1회로 SKU 무제한이고,
"디퓨저(방향제)"로 내면 향마다 27만원에 3년마다 갱신이다.
제품 카테고리를 뭐라고 부르느냐가 총 비용을 수백만원 단위로 바꾼다.

기획 단계에서 이 비교를 자동으로 해주는 도구가 필요하다.

## 기능

1. `classify(intent)` — 제품 의도를 넣으면 가능한 레짐/카테고리를 반환
   intent는 다음을 담는다:
     - 용도(신체 사용 / 공간 / 섬유 / 표면)
     - 주장하는 기능(향, 세정, 탈취, 보습, 살균 등)
     - 제형(액상 / 고체 / 스프레이 / 지속방출)
   → 매칭 규칙은 data/regulatory/classification_rules.yaml 에 두고
     코드에 하드코딩하지 말 것
   → 애매한 경우 여러 후보를 모두 반환하고 "관할 기관 확인 필요"를 명시할 것

2. `compare(intent, sku_count, horizon_years)` — 후보 레짐별 총비용 비교
   출력에 포함할 것:
     - 진입비용 (등록/신고)
     - SKU 확장 비용 × sku_count
     - 갱신 비용 × horizon_years / 갱신주기
     - 총 소요 기간
     - 총 규제비용
   → 표로 나란히 비교하고, 최저 비용 경로를 명시할 것

     - 판정 사유를 반드시 사람이 읽을 수 있는 문장으로 설명할 것

### 프롬프트 13 — 제품 파이프라인 관리

```
brand-lab에 제품별 진행 상태 관리를 추가한다.
제품이 여러 개가 되면 무엇이 어느 단계에 있는지 놓친다.

## 단계 정의
아이디어 → 처방개발 → 안정성시험 → 규제등록/신고 → OEM 견적
→ 파일럿배치 → 본생산 → 출시 → 판매검증 → (존속/철수)

각 단계마다 게이트 조건이 있고, 조건을 못 채우면 다음으로 못 넘어간다.
게이트 조건은 data/pipeline_gates.yaml 에 정의하고 코드에 박지 말 것.

예시 게이트:
- 처방개발 → 안정성시험: 처방 상태가 '확정'이고 DOE 결과가 존재
- 안정성시험 → 규제등록: 45℃ 8주 관찰이 완료되고 판정이 전부 '합격'
- 규제등록 → OEM견적: 등록/신고 번호가 입력됨
- 파일럿 → 본생산: 파일럿 배치 평가가 홈 배치 기준 ±1점 이내
- 출시 → 판매검증: 출시일로부터 6주 경과

## 기능
1. `status()` — 전 제품의 현재 단계를 칸반 형태로 출력
2. `gate_check(product)` — 다음 단계로 갈 수 있는지, 못 가면 무엇이 막고 있는지
3. `blocked()` — 30일 이상 같은 단계에 머문 제품을 경고
4. `kill_check(product)` — 판매검증 단계 제품에 대해 철수 기준 판정
   철수 기준(config에서 조정 가능):
     - 초도 물량 소진율 30% 미만
     - 구매전환율 0.5% 미만
     - 광고 ROAS 200% 미만이 4주 이상
   → 기준 미달이면 "철수 검토" 플래그.
     자동으로 결정하지 말고 판단 근거만 제시할 것.
5. CLI: brandlab pipeline status / gate <product> / kill-check

## 검증
- 게이트 조건 미충족 시 진행이 막히는지 테스트
- 정체 감지가 날짜 기준으로 정확한지 테스트
```

### 프롬프트 14 — OEM 견적 비교 · 스펙시트 생성기

```
brand-lab에 OEM 공장 관리 기능을 추가한다.
집에서 개발한 처방을 공장에 넘겨 양산할 계획이라 이 단계가 중요하다.

## 기능

1. `spec_sheet(formula)` — OEM 전달용 스펙 시트 생성 (마크다운 + PDF)
   포함할 것:
     - 제품 개요, 목표 사용감, 타겟
     - 처방 (원료명 + INCI + %), 상 구성, 공정 온도
     - 목표 물성 (경도, 융점 범위, 외관, 향 강도)
     - 안정성 시험 결과 요약
     - 용기·충전량·라벨 요구사항
     - 필수 요구사항: 파일럿 배치 10~50kg 선행, retain sample 보관
   - 처방 공개 수준을 옵션으로 조절할 것:
     full(전체 %) / partial(핵심 원료만) / spec_only(물성 목표만)
     → NDA 전에는 spec_only로 보낼 수 있어야 한다

2. quotes.yaml — 공장별 견적
   factory_name, 담당자, MOQ, 단가, 리드타임, 파일럿가능여부,
   NDA체결일, 보유설비, 메모

   - 공장별 총비용 (단가 × 수량 + 금형/셋업비)

4. `pilot_compare(home_batch, pilot_batch)` —
   - 홈 배치와 파일럿 배치의 평가 점수를 항목별로 비교
   - 차이가 1점을 넘는 항목을 강조
   - 왁스/버터 비율이 높은 처방이면 "냉각 속도 차이로 인한 결정 구조
     변화 가능성"을 원인 후보로 제시

5. CLI: brandlab oem spec <product> <version> --disclosure partial
       brandlab oem compare <product> --units 1000

## 검증

### 프롬프트 15 — 원료 크로스체크 (레짐별 금지·제한물질)

같은 원료라도 레짐마다 규제가 다르다. 화장품에서 쓸 수 있는 원료가
생활화학제품에서는 제한될 수 있고 그 반대도 있다. 그리고 캔들·디퓨저용

## 기능

1. `cross_check(formula)` —
   해당 제품의 레짐에 맞는 금지·제한 목록과 대조
     - 화장품: data/regulatory/cosmetics/prohibited.yaml, restricted.yaml
     - 생활화학제품: data/regulatory/chemical_safety/prohibited.yaml,
       restricted.yaml
   - 배합한도 초과 시 error, 목록에 없는 원료는 info

     쓰였으면 **error**

   - 이 두 개는 절대 조용히 넘어가지 말 것

3. `ingredient_usage(ingredient_id)` — 역참조
   - 이 원료를 쓰는 모든 처방을 나열
   - 원료를 교체하거나 단종됐을 때 영향 범위를 파악하는 용도

4. `cross_regime_report(ingredient_id)` —
   - 이 원료가 각 레짐에서 어떻게 취급되는지 한 표로
   - "화장품: 사용 가능 / 생활화학제품: 제한 (한도 0.1%)" 형태

5. CLI: brandlab check <product> <version>
       brandlab ingredient where-used <id>

- "이 검사는 등록된 데이터에 대해서만 수행됩니다. 통과가 적법을
  보장하지 않습니다." 문구를 항상 붙일 것

## 검증
- 캔들용 향료(화장품용_등급 False)를 화장품 처방에 넣으면 error가 나오는지 테스트
- 배합한도 경계값에서 정확히 판정되는지 테스트
- 규제 데이터가 오래됐을 때 경고가 나오는지 테스트
