# 플랫폼 확장 설계 — 식품 레짐(food / 건강기능식품)

**목표**: 화장품·생활화학제품을 다루던 brand-lab을 **식품(건강간식)** 까지 확장한다.
단, 이 플랫폼의 원칙 — *레짐(적용 법)을 추상화하고, 규제 수치는 코드가 아니라 YAML에 둔다* — 을 그대로 지킨다.
이 문서는 **구현 가능한 청사진**이며, 실제 코드의 확장 지점(모델·레짐 프로토콜·데이터 스키마)에 매핑돼 있다.

> ⚠️ **먼저 읽어주세요.** 이 문서의 규제 수치·분류·표시항목은 **확인 필요 예시**입니다.
> 식품은 식품위생법·식품표시광고법·건강기능식품법 영역이며, 최종 판단은 **식약처·관할 지자체**가 합니다.
> 각 YAML에 `last_updated`·`source_url`을 반드시 넣고, 출시 전 원문 대조하세요.

---

## 0. 결론 먼저 — 확장은 가능한가?

**가능합니다. 이 플랫폼은 원래 이걸 하도록 설계됐습니다.**

근거(실제 코드):
- `src/brandlab/regimes/base.py`의 `Regime` 프로토콜을 구현하고 `registry.py`의 `_BUILTIN`에 **한 줄** 추가하면 새 레짐이 붙습니다. 화장품법·화학제품안전법이 이미 그렇게 들어가 있습니다.
- 규제 수치는 `data/regulatory/<레짐>/*.yaml`에서 읽습니다 (`RegimeInfo`, `RegimeLabelItems`, `ProhibitedList`, `RestrictedList`, `ClassificationRules` 모델이 이미 존재).
- 배치·원가·DOE·안정성 같은 **레짐 무관 코어**는 식품에도 그대로 적용됩니다.
- 라벨/문구검사 **UI는 이미 레짐 분기**로 리팩터링돼 있어, `food` 레짐을 추가하면 화면이 자동으로 흡수합니다.

**단, 식품에만 있는 새 작업이 세 가지 있습니다** (아래 3·4장): ① 두 개의 식품 레짐, ② 영양성분 계산 모듈(신규), ③ 식품 라벨·알레르기·광고 데이터.

## 1. 무엇을 넣고 무엇을 뺄 것인가 — 식품 규제 레짐 지도

식품은 "건강 주장의 수위"에 따라 적용 법과 비용이 갈립니다. 화장품(일반) vs 기능성화장품, 방향제 vs 살생물제와 **같은 구조**입니다.

| 카테고리 | 적용 법 | 제도 | 진입 부담(예시) | 1인 창업 판단 |
|---|---|---|---|---|
| **일반식품 — 과자·젤리·초콜릿·음료** | 식품위생법 + 식품표시광고법 | 식품제조가공업 **등록** + 품목제조보고 | 낮음(등록 1회 + 품목보고 저비용) | ✅ **바로 추가** |
| **즉석판매제조가공** (매장서 직접 만들어 판매) | 식품위생법 | 즉석판매제조가공업 신고 | **가장 낮음**(소규모 시작) | ✅ 저자본 최적 |
| **특수용도식품** (영유아·체중조절 등) | 식품위생법(별도 기준) | 유형별 기준·규격 | 중간 | ⚠️ 기준 까다로움 |
| **건강기능식품 — 고시형 원료** | 건강기능식품법 | 건기식제조업 허가 + 품목제조신고 | 높음(제조업 허가 시설요건) | ⚠️ 시설·비용 큼 |
| **건강기능식품 — 개별인정형 원료** | 건강기능식품법 | 식약처 개별인정(효능·안전 자료) | **매우 높음**(수억·수년) | ❌ 1인 규모 아님 |
| 의약품 오인(질병 치료 표방) | 약사법 | — | — | ❌❌ 금지 |

### 그래서 답

**일반식품(과자·젤리·저당 간식)은 넣으세요.** 화장품처럼 등록 1회 구조에 가깝고, "불량식품→건강식" 리메이크가 여기 들어갑니다. **저자본 창업에 맞습니다.**

**건강기능식품은 레짐으로 넣되(`health_functional_food`), 대부분 REJECT/CAUTION로 판정하게 하세요.** "혈당·면역·다이어트" 같은 기능성을 주장하는 순간 여기로 넘어가고, 개별인정형은 수억 원입니다. **`advise`가 이 경계를 계산으로 보여주는 게 핵심 가치**입니다 (향수 vs 디퓨저와 동일 논리).

**의약품 오인(질병 치료·예방)은 절대 빼세요.** 약사법 영역이며 식품에 표방 시 위법입니다. `unsupported` 레짐 또는 `lint` high로 차단.

> ⚠️ **플랫폼이 대체 못 하는 것**: 식품은 화장품에 없는 **미생물/식중독 안전, HACCP, 콜드체인**이 핵심 리스크입니다. 이건 처방(formula) 레벨이 아니라 **시설·공정** 문제라, 이 도구는 *추적·체크리스트*만 하고 시험 자체를 대체하지 않습니다. (특히 아이스크림 등 냉동식품은 콜드체인 때문에 저자본에 불리 → 상온 유통 간식 권장.)

## 2. 아키텍처에 어떻게 붙는가 — 재사용 vs 신규

실제 코드 기준으로 "그대로 되는 것"과 "새로 만들 것"을 나눕니다.

| 계층 | 파일/모델 | 식품 확장 시 |
|---|---|---|
| 처방·배치 | `core/models.Formula`, `batch` | ✅ 그대로 (배합 100%·g 환산 동일) |
| 원가·손익·MOQ | `cost` | ✅ 그대로 |
| 실험 DOE | `doe` | ✅ 그대로 (관능 패널 DOE) |
| 안정성 | `stability` | ✅ 개념 그대로 → **유통기한(소비기한) 시험**으로 |
| 라벨 UI | `pages/2_라벨.py` | ✅ **이미 레짐 분기** — food 뷰 자동 흡수 |
| 문구검사 UI | `pages/6_문구검사.py` | ✅ **이미 도메인 선택** — food/ad_terms.yaml 자동 노출 |
| 레짐 프로토콜 | `regimes/base.Regime` | ✅ 그대로 구현 |
| 레짐 등록 | `regimes/registry._BUILTIN` | ⚠️ **한 줄 추가** (`"food": FoodRegime`) |
| 규제 판정 | `advisor` + `classification_rules.yaml` | ⚠️ **규칙 추가** (food/hff) |
| 라벨 항목 | `RegimeLabelItems` | ⚠️ **food label_items.yaml 신규** |
| 광고 표현 | `AdTermList` | ⚠️ **food/ad_terms.yaml 신규** |
| **영양성분 계산** | — | ❌ **신규 모듈** (칼로리·당·나트륨·단백질) |
| **식품 알레르기 22종** | `allergens.yaml`은 화장품 26종 향료 | ❌ **food 알레르기 데이터 신규** |
| 원료 영양 데이터 | `core/models.Ingredient` | ❌ **모델 확장 필요** (아래 3-6) |
| product_type | `ProductType`(rinse_off/leave_on) | ⚠️ 식품엔 무의미 → placeholder (디퓨저와 동일) |

> ⚠️ **`extra="forbid"` 주의**: `Ingredient`·`Formula` 모델은 임의 필드를 거부합니다. 영양성분을 넣으려면 모델에 **필드를 명시적으로 추가**하거나 **별도 데이터 파일**로 분리해야 합니다(3-6 참조).

## 3. 데이터 설계 (YAML 스키마)

모든 파일은 기존 pydantic 모델 스키마를 따릅니다. 규제값은 **예시**이며 식약처 원문으로 교체해야 합니다.

### 3-1. `data/regulatory/food/regime.yaml` — 일반식품 (RegimeInfo)

```yaml
code: food
law_name: 식품위생법
display_name: 일반식품
supported: true
entry_cost: 28000            # 식품제조가공업 등록면허세 등(예시·지자체별 상이)
lead_time_days: 14           # 등록·품목제조보고 소요(근사)
sku_expansion_cost: 0        # ★ 품목제조보고는 저비용 → 화장품처럼 SKU 확장 부담 낮음
renewal_period_years: null   # 정기 갱신 없음(영업 유지 기준)
notes:
  - "품목마다 '품목제조보고'가 필요하지만 비용 부담은 낮다(지자체 확인)."
  - "미생물·이물 등 안전은 별도 시설·공정(HACCP) 문제 — 이 도구가 대체하지 않음."
last_updated: 2026-08-24
source_url: "https://www.mfds.go.kr/  # 식품위생법·영업등록 — 실제 URL로 교체"
```

### 3-2. `data/regulatory/health_functional_food/regime.yaml` — 건기식 (RegimeInfo)

```yaml
code: health_functional_food
law_name: 건강기능식품에 관한 법률
display_name: 건강기능식품
supported: true             # 지원하되 advise/feasibility에서 대부분 CAUTION/REJECT
entry_cost: 3000000         # 건기식제조업 허가·시설요건 근사(예시, 실제 훨씬 큼)
lead_time_days: 60
sku_expansion_cost: 500000  # 품목제조신고(고시형) 근사. 개별인정형은 수억·별도
renewal_period_years: null
notes:
  - "개별인정형 기능성 원료는 식약처 인정에 수억 원·수년 → 1인 규모 아님."
  - "고시형 원료를 쓰더라도 제조업 허가 시설요건이 큼."
last_updated: 2026-08-24
source_url: "https://www.mfds.go.kr/  # 건강기능식품법 — 실제 URL로 교체"
```

### 3-3. `data/regulatory/food/label_items.yaml` — 식품 표시 필수항목 (RegimeLabelItems)

화장품 '전성분'과 완전히 다릅니다. `label_spec()`이 이 목록을 반환합니다.

```yaml
last_updated: 2026-08-24
source_url: "https://www.foodsafetykorea.go.kr/  # 식품표시광고법 표시기준 — 교체"
items:
  - { key: product_type,   label: "식품유형(예: 과자류·캔디류/젤리)", required: true }
  - { key: business,       label: "업소명 및 소재지", required: true }
  - { key: expiry,         label: "소비기한(구 유통기한)", required: true }
  - { key: net_weight,     label: "내용량(및 열량)", required: true }
  - { key: ingredients,    label: "원재료명(함량 순)", required: true }
  - { key: nutrition,      label: "영양성분표(열량·나트륨·탄수화물·당류·지방·단백질 등)", required: true }
  - { key: allergen,       label: "알레르기 유발물질 표시(해당 시)", required: true }
  - { key: gmo,            label: "유전자변형식품 표시(해당 시)", required: false }
  - { key: origin,         label: "원산지 표시(해당 시)", required: false }
  - { key: caution,        label: "부정·불량식품 신고, 보관방법 등 주의사항", required: true }
```

### 3-4. `data/regulatory/food/allergens_food.yaml` — 알레르기 유발물질 (신규 스키마)

화장품 향료 알러젠(26종)과 목록이 다릅니다. **식품 22종**을 별도로 둡니다.

```yaml
last_updated: 2026-08-24
source_url: "https://www.foodsafetykorea.go.kr/  # 알레르기 표시대상 — 교체"
# 표시대상(확인 필요 예시): 알류(가금류)·우유·메밀·땅콩·대두·밀·고등어·게·새우·
#   돼지고기·복숭아·토마토·아황산류·호두·닭고기·쇠고기·오징어·조개류(굴/전복/홍합 등)·잣
allergens:
  - { id: milk,   name: 우유,   keywords: [우유, 유청, 카제인, 분유] }
  - { id: soy,    name: 대두,   keywords: [대두, 콩, 두유, 대두단백] }
  - { id: wheat,  name: 밀,     keywords: [밀, 밀가루, 글루텐] }
  - { id: peanut, name: 땅콩,   keywords: [땅콩] }
  - { id: egg,    name: 알류,   keywords: [난, 계란, 난백, 난황] }
  # … 나머지 표시대상을 원문으로 채울 것
```

> 원료가 알레르기 물질을 포함하면 `Ingredient`에 매핑이 필요합니다(3-6). 화장품 `allergens` 필드(향료용)와 **별개**로 둡니다.

### 3-6. 원료 영양성분 — 모델 확장 (핵심 신규)

`Ingredient`는 `extra="forbid"`라 임의 키를 못 넣습니다. **두 가지 방법** 중 택1:

**방법 A (권장) — `Ingredient`에 선택적 중첩 필드 추가.** 데이터 지역성이 좋음.

```python
# core/models.py 에 추가
class FoodNutrition(BaseModel):
    model_config = ConfigDict(extra="forbid")
    kcal_per_100g: float = Field(ge=0)
    protein_g: float = Field(default=0, ge=0)
    fat_g: float = Field(default=0, ge=0)
    carb_g: float = Field(default=0, ge=0)
    sugar_g: float = Field(default=0, ge=0)
    sodium_mg: float = Field(default=0, ge=0)
    food_allergen_ids: list[str] = Field(default_factory=list)  # allergens_food.yaml 참조

class Ingredient(BaseModel):
    ...
    nutrition: FoodNutrition | None = None   # 식품 원료만 채움. 화장품 원료는 None
    food_grade: bool = False                 # 식품용 등급(화장품 cosmetic_grade와 대칭)
```

**방법 B — 별도 파일** `data/food/nutrition.yaml`을 원료 id로 키. 화장품 모델을 안 건드림.

```yaml
# data/food/nutrition.yaml
nutrition:
  oat-flour:  { kcal_per_100g: 389, protein_g: 16.9, carb_g: 66, sugar_g: 1, sodium_mg: 2 }
  whey-protein: { kcal_per_100g: 400, protein_g: 80, food_allergen_ids: [milk] }
  allulose:   { kcal_per_100g: 20,  carb_g: 90, sugar_g: 0 }   # 저당 대체감미료
```

> **권장: 방법 A.** 원료 한 곳에서 물성·단가·영양을 함께 보는 게 낫고, `grade: food`와도 일관됩니다.
> 단 이건 **레짐 무관 코어 모델 변경**이므로 P-Food-1(리팩터링)에서 기존 테스트가 깨지지 않는지 확인해야 합니다(선택 필드라 하위호환).

### 3-7. `data/regulatory/classification_rules.yaml` — food 분류 규칙 추가

기존 파일에 규칙만 추가합니다(`use`에 섭취용 토큰 `ingest` 신설).

```yaml
  # --- 섭취 + 영양(일반식품) ---
  - match: { use: ingest, claim: nourish }
    candidate: { regime: food, category_label: "일반식품(과자·젤리 등)" }
  - match: { use: ingest, claim: low_sugar }
    candidate: { regime: food, category_label: "일반식품(저당 표방 — 표시요건 확인)" }
  # --- 섭취 + 기능성 주장(건기식으로 넘어감) ---
  - match: { use: ingest, claim: [blood_sugar, immune, weight_loss] }
    candidate:
      regime: health_functional_food
      category_label: "건강기능식품(기능성 주장)"
      note: "기능성 표방은 건기식 인정 필요 — 개별인정형은 수억·수년. 관할 확인"
```

## 6. 검증 기준 (골든 케이스)

- **레짐 분기**: 식품 처방을 라벨 페이지에서 골랐을 때 화장품 전성분이 아니라 **식품 표시항목**이 나온다.
- **advise 경계**: "섭취+영양(일반식품)" vs "섭취+혈당(건기식)"의 총 규제비용이 나란히 비교되고, 건기식 경로가 훨씬 비싸다고 계산된다. (향수 vs 디퓨저와 동일한 가치.)
- **영양 계산**: 저당 젤리 처방의 당류 g이 손계산과 일치하고, 알룰로스 등 대체감미료를 쓰면 당류가 낮게 나온다.
- **문구검사**: food 도메인에서 "면역력·다이어트"가 high로 차단된다.
- **하위호환**: 기존 화장품/화학 테스트가 전부 통과한다(코어 모델 변경이 선택 필드라서).

## 7. 만들면서 경계할 것

1. **도구 만들기가 일이 되는 함정.** P-Food-1~3만 있으면 "저당 간식 한 개"는 개발됩니다. P-Food-4·5(건기식·광고)는 실제로 그 단계에 도달했을 때 만드세요.
2. **식품 안전은 이 도구 밖이다.** 미생물·이물·HACCP·콜드체인은 시설·공정 영역. 이 플랫폼은 배합·원가·영양·표시·규제비용만 다룹니다. **식중독 리스크를 계산이 막아주지 않습니다.**
3. **저자본이면 상온 유통 + 즉석판매제조가공부터.** 아이스크림(냉동)은 콜드체인 물류비·폐기 리스크가 커서 뒤로 미루는 게 현실적입니다.
4. **규제 수치는 예시입니다.** 이 문서의 등록비·시험비·표시항목·알레르기 목록은 **확인 필요값**입니다. YAML에 `source_url`·`last_updated`를 넣고, 실제 신고 전 식약처·관할 지자체에 확인하세요.
